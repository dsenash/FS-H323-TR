# Разбор дампов (проход 0)

Все сообщения в дампах — фиксированные шаблоны. Между вызовами меняются только:
* call reference (байты 2–3 Q.931);
* GUID callIdentifier / conferenceID (4 байта + 1 байт; остальное постоянно);
* в ALERTING/CONNECT fastStart-ответа — RTP-порты и адрес шлюза принимающей стороны;
* в H.245 MSD-кадрах — 1–3 байта (statusDeterminationNumber и подобное).

Порядок сообщений вызова (звонящая АТС = .193, принимающая = .6), размеры Q.931 в байтах:
SETUP 283; CALL_PROC 109; ALERTING 166; FACILITY 111 (TCS принимающей), 56 (MSD); FACILITY 119 (TCS звонящей), 56 (MSD),
52/51 (ack TCS, ack MSD) в обе стороны; FACILITY 55 (последний от звонящей); CONNECT 146; отбой FACILITY 51 + RELEASE COMPLETE 46 (cause 16).

Вывод для реализации: строить сообщения по шаблонам с заменой полей; разбирать входящие по структуре.
Полный PER-декодер нужен только для SETUP (fastStart: адрес/порт RTP звонящей стороны, кодеки) и для H.245 (TCS/OLC).
Порядок байт кодека fastStart и содержимое TCS ещё требуют побитового разбора (проход 1).

# Дамп h323_out_pn4.pcap (снят на .193, 567 с) — проход 0b

* Calling number теперь есть: Q.931 IE `6c 05 00 80 "101"` (type/plan 0x00, presentation 0x80) перед called `70 04 81 "102"`. SETUP = 290 байт.
* Нет номера (999): после CALL PROCEEDING сразу RELEASE COMPLETE, Q.931 cause **1** (`08 02 81 81`), без ALERTING и без H.245.
* Занято: CALL PROCEEDING, затем RELEASE COMPLETE cause **17** (`08 02 81 91`). Формы UUIE у всех RC одинаковые.
* Отбой в обычном вызове: FACILITY(endSession) + RC cause 16 (`08 02 81 90`).
* DTMF 0–9: звонящая АТС шлёт **H.245 UII внутри туннелированных FACILITY** (12 кадров по 48 байт на 10 цифр: 10 signal + 2 повтора/signalUpdate),
  примерно через 0.5–1 с одна от другой. RTP в дампе нет, поэтому не видно, дублируется ли цифра в RFC 2833.
* Простой: на неактивном соединении только TCP-пакеты без данных (keepalive/ACK, обе стороны, интервал неровный, 15–45 с). Q.931 STATUS ENQUIRY нет.
* STATUS с глобальным call reference (callstate 0): `cause 16` от .6 (t=246 с), в ответ .193 шлёт `cause 31`, затем `cause 16` (как при возврате транка в обслуживание). Причина запроса от .6 неизвестна.

## Дампы 2111 (кодеки и DTMF), 21.11.2026
- `2111-Al.pcap` — только G.711A; `2111-Ml.pcap` — только G.711μ (в конце ещё вызов 6 -> 193, called=101, кодек μ, DTMF с обеих сторон);
  `2111-AMl.pcap` — A и μ вместе. Вызов 101 -> 102 с .193, дальше DTMF.
- **Кодек в fastStart** — один байт в каждом OLC: шаблон `(0c|4c) cc 13 80`, cc = 0x20 (G.711A) или 0x60 (G.711μ).
  SETUP с одним кодеком: UUIE 193 байта (2 OLC), с двумя: 244 (4 OLC: A, A', μ, μ'). ALERTING (ответ) всегда с одним кодеком:
  при предложении A+μ АТС выбрала A (первый в списке). CONNECT кодека не содержит.
- **TCS (H.245)**: один кодек — PDU 64 байта, байт кодека 0x40 (A) / 0xc0 (μ) после `30`; два кодека — PDU 72 байта.
  Обе стороны шлют одинаковый TCS (раньше казавшееся различие «caller/callee» было различием одиночный/двойной).
- **UII** подтверждён для `1-9 0 * #`: `*` = 0x2540, `#` = 0x2460 (формула `(c<<5)|0x2000` верна). Повторы цифр в AMl — повторные нажатия.
  A-D по-прежнему не проверены.
- Реализация: шаблоны `setup` (двойной), `setup1`, `alerting` (патч `AA_TP_CODEC`), `tp_pdu_tcs1`/`tp_pdu_tcs_dual`;
  `aa_tr_msg_t.codecs` (AA_TR_CODEC_A|U). Все 250 кадров из 7 дампов проходят parse -> build побайтно, 726 проверок.
- Правило ответа (план): выбрать первый кодек из предложенных, который совпадает с `codec` транка; нет совпадения — отбой (cause 65/88).
